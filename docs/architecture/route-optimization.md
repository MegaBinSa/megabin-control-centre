# Route Optimization architecture

Phase 2B refines a Draft/Ready baseline through separate provider-neutral Routing and Optimization contracts. Routing supplies point estimates, matrices, ordered-route legs, static-road duration/distance, geometry, capability, and health. Optimization consumes only internal vehicles, depots, windows, capacity, stops, eligibility, service duration, and deterministic seed; adapter boundaries translate any future vendor payload. No production vendor is selected in this phase and no credentials are required. Local, staging, and CI use deterministic fake adapters; production activation remains an explicit deployment/provider ADR decision.

An Optimization Attempt records a safe input snapshot/signature, source version, providers and adapter version, actor, correlation ID, lifecycle (`Pending`, `Running`, `Succeeded`, `Failed`, `Cancelled`, `Superseded`, `Accepted`, `Rejected`), candidate result, comparison, warnings, and safe failure classification. Provider output is independently checked for request-owned, nonduplicated stops before it can succeed. Failure leaves the source Route Version unchanged; the deterministic baseline and manual planning remain clearly labelled fallbacks.

Accepting a succeeded candidate transactionally creates a new Draft Route Version with source lineage, static-road metrics, and internal GeoJSON LineString geometry. It never mutates a source or Published version and never publishes automatically. Rejecting preserves the source. Geometry categories remain distinct: baseline schematic, provider road geometry, and future GPS trail.

Hard constraints are region, locked/fresh roster input, request-owned identifiers, one assignment per stop, team eligibility, capacity, usable operating window, valid resources/coordinates, depots, and sequence integrity. Soft objectives are feasibility first, then after-hours risk, travel duration/distance, territory continuity, preferred team, and balance. There is no programmable objective language.

Only transient and rate-limited failures receive bounded retries; authentication, invalid-request, permanent-constraint, and invalid-response failures require intervention. Timeout, request size, concurrency, retry count, provider selection, mode, and fallback are ordinary non-secret configuration. API credentials belong only in environment-isolated Supabase Edge Function secrets. Usage records store provider, capability, counts, duration, outcome, and optional billing units—not route payloads.

The contracts reserve special-stop location, duration, capacity-reset, and eligibility concepts for future dump planning without defining dump rules. `traffic_aware` is a future routing estimate mode and advisory input, not Route Plan identity or actual history. Phase 2B does not implement live traffic, GPS, Driver PWA execution, or live re-optimization.
